# Event-calendar reminder design — work in progress

Reuse the local notebook visual language from cycle-tracker (warm paper, subtle ruling, blue ink and muted rose accents), but NEVER read or display medical state for event calendars. Event content comes from confirmed event records, not cycle data. Public/image APIs are unnecessary: Pillow renders locally.

## Current traffic, not a forecast

The owner explicitly rejected a future traffic forecast as a requirement. For the event-reminder design, use the current Yandex route estimate at the time the image/reminder is generated and label it as current travel time, not tomorrow's predicted traffic. Record when it was retrieved; a stale estimate must not silently look live. Keep driving time separate from taxi pickup/waiting time unless that was actually obtained. Compute any suggested departure from the event start, current route duration and an explicitly shown planning buffer; do not pretend the buffer came from Yandex. Do not block the design on access to future-departure controls or a forecasting API. This requirement does not itself prove that the scheduled renderer or traffic lookup has been integrated.

## Day-before notification

The latest viewport rule is **one hour before the recommended departure**, superseding the earlier three-hours-before-event left boundary. For example, departure18:10 means axis start17:10. Do not show the full00:00–24:00 day. Enlarge the key times and axis labels. Hatch only the event marker/known event interval, leaving preparation/travel/free time unhatched, and mark departure separately. A true event-duration band requires a verified end time/duration; do not silently substitute the one-hour margin as the concert duration. Clarify the missing duration/end and whether the trailing hour is after the start or the end when that distinction changes the drawing. Keep the exact event start separate and label any provisional travel estimate/buffer. Relative “tomorrow” must agree with the preview/reference date. The earlier full-day PNG and its whole-window fill are superseded drafts, not the approved design.

Current private prototype: manager `workspace/event-calendar-prototype/render_day_reminder.py`, test `test_render_day_reminder.py`, current output `day-before-timeline-v4.png` (1080×1640 portrait for the owner's iPhone, not a square). Key times and labels are larger, and the layout uses the upper and lower screen areas. Do not reintroduce the removed image notes: “За час до выезда”, “Окончание концерта не указано”, “Отмечено начало — длительность не придумана”, or the “Эскиз · время по Москве · уведомление не отправлено” footer. The axis starts one hour before the computed departure; the current draft's right boundary remains one hour after the event start while its actual end is unknown. The departure marker is computed from a separately obtained current route estimate plus a displayed buffer. Because no event end is confirmed, hatching currently marks only the start label, not an invented duration band. Do not describe that as a known complete event interval or tomorrow's traffic forecast. It uses the existing notebook font/palette without cycle state. A real PNG was rendered and visually checked; cropped-axis/date/departure geometry is tested. This prototype explicitly rejects windows crossing midnight rather than hiding overflow. Do not claim such cases are already supported.

## Text under the picture

Accompany the picture with a caption **below** the image. The owner corrected “завуалировать” to **“акцентировать”**: emphasize the important event/departure/start details in bold; do not hide them under spoilers. Make the destination name a Yandex Maps link and put its full address on the immediately following line in inline monospace for copying. Keep address and link pointed at the venue, not the private origin. Distinguish a cached observed driving estimate from a new live lookup; the preview's current route evidence records when it was observed. A native Telegram photo caption supports bold, text links and inline code; with the Bot API use HTML entities/parse mode and `show_caption_above_media=false`, `has_spoiler=false`. Avoid sending a second copy of an image already delivered directly. The local preview caption is `workspace/event-calendar-prototype/day-before-caption.html`.

The monthly event-calendar prototype is `render_events.py` in the same private workspace; it currently supports up to two event-bearing months and four events, with a numbered agenda. These are review drafts, not installed notification renderers. Their existence does NOT modify cron prompts or prove that scheduled messages attach an image. Keep that integration separate, preserve the existing seven reminder jobs/routes/times, and verify the actual scheduled entrypoint when it is explicitly adopted.
