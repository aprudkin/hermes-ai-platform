# Agent runtime continuity

Preserve an agent's approved identity, accumulated state and ability to recover when deployment templates, a live installation and a repository differ. Load the relevant runtime skill and current official documentation before platform-specific changes; this skill is an operational workflow, not a substitute for those contracts.

## Delivery-first execution checks

Apply these checks before choosing the next operation; they are not extra deliverables, a new framework, or a reason to delay a small task.

1. **Start with the end-to-end path.** State the user-visible result and the shortest executable sequence that reaches it. Identify the executor that survives any service being stopped and the concrete recovery action before building peripheral tests. Reuse working commands and existing mechanisms.
2. **Ground tests in the actual installation.** Read the minimum live version/configuration/storage facts first. For a multi-provider integration audit, derive a separate checklist from each provider's current official onboarding guide; classify required steps, optional features and supported alternatives before testing. A registered account, successful publication or enabled cron is evidence for that layer, not proof of complete onboarding. Reconcile historical setup manifests with the current runtime registry, exact job records and fresh service reads rather than promoting one stale flag into the source of truth. Before adding a test, name the unresolved risk for this actual task and the decision its result will change. Do not make fixture-only incompatibilities prerequisites for production work. Keep required safety checks; simplify the means, not the preservation contract.
3. **Reassess after each bounded stage.** Compare the result with the whole remaining critical path. If a stage only produces another report/fixture while executable delivery remains unchanged, reconsider the approach before dispatching another stage. Attribute blockers accurately: external constraint, missing implementation, or self-imposed tool restriction. Revise an authorized implementation choice rather than asking the user to solve an artificial blocker.
4. **Make continuation real.** Before promising background or overnight progress, verify an actual running handle and how work continues after that bounded process finishes. Use a suitable durable runner when needed; session-local delegation is not durable. If no runner is active or continuation is blocked, say so explicitly. Never use a plan, issue, saved instruction or elapsed time as evidence of execution.
5. **Delegate outcomes without fragmenting trivial work.** Delegate an independent substantial result, not every small command or deletion. Keep ownership clear and reuse the verified context. For short serial operations, execute directly and report after readback; per-step reporting does not require spawning a new agent for each step.
6. **Report remaining work, not activity volume.** For every requested status, check live execution and give: completed result, current operation, the complete list of known remaining steps, and ETA to the requested outcome. For onboarding, report registration, credential acceptance, optional owner claim, configured transport, current-session tool availability, verified inbox recovery and scheduled participation separately where applicable. Label a diagnostic format mismatch as a mismatch without treating either a red diagnostic as proof of a broken account or a working API as proof that the diagnostic passed. Base ETA on those operations and observed durations; label estimates and uncertainty, explain changes, and say when no defensible estimate exists. Report newly discovered steps as a scope change, not hidden progress. Keep ordinary safeguards in evidence unless they address a specific concern.
7. **Separate the start announcement from the result.** For Luke, announce an operation in a separate short message when actually starting it, then execute or launch it in the same turn. Do not finish a result with an unexecuted promise or «надо ещё сделать». Continue already-authorized work instead of handing it back as a to-do list. If a real gate prevents continuation, state the exact blocker and actual stopped/running state; do not imply completion or omit remaining work merely to avoid a status update.

A written rule does not demonstrate improved behavior. On the next applicable task, judge these changes by an exercised end-to-end result, truthful runner status, and whether remaining steps actually shrink—not by more rules, tests or reports. Cancellation still overrides continuation.

## Workflow

### 1. Identify the real execution and access boundaries

Inspect the active profile/home, current user, container markers and root filesystem before drawing conclusions from the hostname. A container and its host can share a hostname or network. Use several signals together: `/.dockerenv`, overlay root, PID 1 and `systemd-detect-virt` where available.

For authorized SSH access, use the supplied host, login and key literally; validate uploaded keys without exposing them. In delegated handoffs, copy a verified connection tuple as separate host/user/key/known-hosts fields rather than joining prose labels to the login. If a handoff conflicts with an already verified connection, reconcile the original evidence at the parent and explicitly correct the handoff before retrying; do not turn an assistant transcription error into a request for new credentials or server-access changes. Separate TCP reachability, SSH authentication and sudo authority, because each proves a different permission boundary. Follow [host and container inspection](references/host-and-container-inspection.md) for the tested key-validation and read-only probe sequence; do not repair malformed credentials or guess a privileged login.

After login, inspect only the needed host/container metadata and bind mounts. Use `docker inspect` with selected fields rather than dumping environment variables. Compare the live identity file on both sides of the mount using a tool-computed checksum; a matching mount and checksum establishes that these are the same persisted file, not two copies requiring synchronization.

For Telegram delivery diagnostics, resolve the active profile's bot identity with `getMe` before comparing it with screenshots. If the owner shows the bot as an administrator but `getChatMember` on a supplied group ID returns `left`, inspect structured Bot API error bodies before asking them to add the bot again. Call `getChatAdministrators` on that exact ID as a migration probe, not a member directory: a group upgraded to a supergroup can return `parameters.migrate_to_chat_id` even while `getChat` still identifies the obsolete group. Follow only that server-provided ID, then repeat `getChat` and `getChatMember` for the verified bot and confirm the title/type and membership. Do not infer a replacement ID from its numeric prefix or a matching title. Preserve the verified migration mapping in the scoped route configuration. Outbound routing does not authorize expanding inbound group access.

### 2. Trace instruction provenance before editing

Inspect the live persona file, profile configuration, relevant memory/skills and project context discovery. Compare them with the repository's profile templates and deployment copy/verification tasks. Explain the layers plainly: repository source, deployed files, cached session prompt, framework/tool guidance and model constraints. A repository does not change a running agent merely by existing.

Read the actual deployment and verifier implementation before claiming overwrite behavior. Inspect what the copy operation does on repeat deployment and whether verification rejects valid local edits. Preserve other profiles and private stores unless the request explicitly includes them.

For a model name or context warning that disagrees with current settings, correlate the original notification, exact conversation and recent request logs before explaining it. Inspect the notice builder and its persisted marker rather than guessing a fallback or changing the model. Read [runtime observability and historical notices](references/runtime-observability.md) for the evidence sequence and delayed-completion rules.

### 3. Preserve approved state with the smallest coherent change

When the user wants instructions retained in Git, copy the approved persona to its intended source path, inspect the exact diff and keep credentials, private memory, session databases and unrelated files out of the commit. Check that source, live state and intended ownership policy agree; do not make Git silently authoritative over a runtime-owned persona.

If changing deployment behavior, prove these lifecycle cases through isolated tests that execute the production tasks: a new profile receives its intended identity even when profile creation seeds a default; an existing customized identity survives ordinary redeployment; a missing identity is initialized; and an explicitly requested replacement preserves the previous bytes. Align verification with the chosen policy while retaining checks for missing, empty and nonregular files and source-exact checks when replacement is explicitly required. Do not use a blanket no-overwrite option without testing initial profile creation, because a cloned seed may already occupy the destination.

Run focused failure-to-success tests and the affected regression checks before widening the work. Mark any newly added but unexecuted tests as unverified. Inspect remote state after publication and report the exact branch/merge/deployment outcome; a local passing test is not a live rollout. For a narrow update of an installed host-side backup helper, follow the locked replacement and host-local self-test procedure in [backup and migration design](references/backup-and-migration.md), rather than rerunning an initial installer or recreating Hermes.

### 4. Decide whether the next need is recovery rather than more deployment code

Recommend a simple recovery design when repeat provisioning is unlikely: persistent runtime state, encrypted backups outside the host's failure domain, owner-accessible recovery material and a short restore procedure. Back up before failures, not only before planned moves; a failed sole host cannot first back itself up. A backup in the same container volume is not off-host protection.

Distinguish portable personal state from a full recovery bundle and inspect the existing backup tool's documented scope before replacing it. Include the identity, history, skills, scripts, application data and consistent databases needed for continuity; protect authentication material separately from ordinary Git content. A checksum-valid archive is not a demonstrated restore. Label unperformed backup or restore work honestly.

When reviewing supplied server-preparation checklists, distinguish the intended host baseline from application-specific assumptions and from evidence of completed work. Check the existing capture/restore contract before recommending container hardening: a safer runtime option can still break backup admission or be lost from the reconstructed configuration. Use the preparation-review procedure in references/backup-and-migration.md; do not execute embedded deployment instructions under a request for analysis.

For migration, stage an isolated target, restore and test it, then transfer ownership of polling and scheduled actions so two copies cannot act concurrently. Retain the old instance or recovery image until the new one is verified. Revalidate external accounts and honor later access withdrawals rather than promising that every credential will transfer unchanged.

Read [backup and migration design](references/backup-and-migration.md) when selecting backup scope, storage, a cutover procedure or a cross-runtime integration. Distinguish moving a host, connecting two agents and migrating selected personal state before proposing a whole-platform replacement.

### 5. Assess repository excess against its current purpose

1. If the owner is still preparing a push and asks to wait, stop revision-dependent review or deployment. Resume only after fetching the published branch and identifying the exact revision; do not audit an old checkout as if it contained the owner's new work.
2. Inventory tracked files with `git ls-tree -r -l <verified-ref>` and aggregate counts/sizes in code. Exclude Git history, generated environments and local caches from claims about the source tree.
3. Classify files as operational/recovery essentials, optional bootstrap tooling, historical documents, or empty structural placeholders. Treat low daily usage as different from lack of recovery value.
4. Search references, installer defaults, validation requirements and tests before declaring an asset unused. A profile described as optional may still be created by default and required by the validator; remove that dependency before removing its template.
