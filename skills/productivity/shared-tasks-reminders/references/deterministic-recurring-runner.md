# Deterministic recurring runners

Use a small profile-local runner instead of LLM interpretation when a reminder has resource-level completion, membership-sensitive fallback, and idempotent direct delivery. Keep the task register canonical; scheduling remains the parent's responsibility.

- Inspect the active profile's real `state.db` read-only before defining an acknowledgment reader. Group session user IDs may be null. Hermes currently stores `[name|numeric_id]` prefixes and `[Replying to: "..."]` quote context, not reliable per-message reply-to IDs. Require a real inbound platform ID, authorized anchored sender, role=user, active row, and allowed origin chat. Never search arbitrary content for authorization.
- Include a unique task/cycle/ordinal marker in sent text and persist exact sent text plus returned chat/message IDs. If reply IDs are not stored, count bare completion only from an exact matching reminder quote. Ignore historical pre-activation completions, questions, promises, negation, quotes/reported speech, uncertainty, and delivery-failure language.
- Persist per-resource pending state, acknowledgments, counters, attempts, and receipts under the one canonical task. Use atomic replacement/fsync and a stable sidecar flock. Re-read/merge immediately before writes so slow delivery does not revert unrelated task edits. Other writers must cooperate with the same lock for full concurrency safety.
- Persist intent before Telegram side effects and successes immediately afterward. Telegram Bot API has no send idempotency key or getMessage read-back. Hold ambiguous timeout/crash attempts for manual reconciliation instead of blindly retrying or falling back to DMs; this avoids duplicates without pretending exactly-once is achievable.
- Route known group members to group and departed/unknown users privately. After any recipient is successfully served for an occurrence, retry only unserved private destinations, even if membership recovers: a new group message tagging both would duplicate the known success.
- Keep dry-run zero-network and zero-state-write; require explicit execution opt-in. Direct-delivery cron runners must print nothing on success/nondue ticks; expose structured reports only on request. Never create cron or alter configuration as an incidental test.
- Preserve closed-window overdue state without claiming the submission window remains open. At the next monthly cycle, consolidate outstanding context into one current reminder rather than running separate overlapping queues.
