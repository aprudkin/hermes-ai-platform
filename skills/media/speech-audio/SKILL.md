# Speech generation and voice-message delivery

Produce the requested playable audio, not merely a transcript or an explanation of how to synthesize it. This skill covers output speech; use youtube-content for captions-first video analysis and hermes-agent for persistent voice configuration.

## Le's private-chat delivery preference

In Le's own Telegram DM, provide ordinary answers in BOTH written text and a native voice message. Reports are the exception: deliver reports, including accounting summaries and numbered payment lists, ONLY as text, without a spoken duplicate. Keep this recipient- and chat-scoped; do not apply it to Luke, groups, scheduled reports or other destinations. A later explicit request for a particular response overrides the standing format.

Prepare the final written answer before synthesis so the audio reflects the same facts, qualifications and latest user corrections. For ordinary answers, speak a natural version without reading Markdown, citation numbers, raw URLs or MEDIA directives; retain the full written answer and its sources. If the user changes the scope while a clip is being generated, do not deliver the stale clip—generate or reuse only audio matching the revised answer. Classify a message as a report before synthesis so long financial lists never become unwanted recordings.

## Selected voice preferences

Luke selected Deepgram Flux TTS, Russian Vladimir (`flux-vladimir-ru`), and settled on default speed **0.5** after comparing samples. Use the direct `deepgram` route at that supported rate; the optional `deepgram-tempo` wrapper is only for below-minimum requests such as0.4. Incoming voice recognition is a separate setting: Deepgram `nova-3`, Russian `ru`. New explicit instructions override these preferences. For a personal voice note intended for Le, an instruction to show Luke a variant first authorizes only a preview in his chat; wait for his send instruction, then send that exact approved artifact rather than regenerating it.

## Procedure

1. **Resolve text and message boundaries first.** Preserve the supplied wording, language and order; do not add a greeting, explanation or outro to spoken text. When Luke replaces a creative draft with an exact script, synthesize that script instead of continuing to embellish it; unwanted phrasing and unwanted delivery are separate corrections. Treat editing instructions such as adding a sentence as instructions, not words to pronounce. When Luke explicitly combines an earlier recording with new text, produce one complete revised voice note without speaking the editing instruction. Otherwise, default separately supplied quoted phrases to separate messages; an explicit second or third message is a new clip. Treat corrections to wording separately from corrections to message count. When an attached or replied-to audio is the source, process that exact attachment rather than guessing its contents from surrounding chat.
2. **Use the configured speech tool first.** Call text_to_speech with the exact requested text. For a one-off recording request, do not enable speech globally, change inbound recognition, or alter provider configuration. Honor an explicit standing recipient-specific delivery preference through the response workflow instead of changing unrelated chats' settings. During a speech-rate adjustment, interpret a bare decimal as the next requested default rate; accept Russian decimal commas, preserve voice/language/STT, save through supported config setters, and test without a per-call speed override so the saved default is actually exercised. Reply with a short confirmation and one sample, not a repeated setup report. Use [speech-rate adjustment](references/speech-rate.md) for native limits and pitch-preserving post-processing; load hermes-agent before persistent Hermes configuration.
3. **Keep logical messages distinct from service chunks.** A service may require multiple synthesis chunks for one long message; concatenate only those chunks belonging to that message. Never merge separate requested messages merely because they arrived in the same conversation. Save generated parts so a boundary correction can be handled by reusing audio rather than synthesizing everything again.
4. **Recover narrowly from a service failure.** An error or empty output is not a recording. For a transient synthesis server error, retry once before changing provider or implementation; report a persistent failure rather than treating saved settings as a successful audio test. Try a bounded, actually available alternative without repeated identical requests. For short non-sensitive text, the public Google Translate TTS method in [short-form synthesis](references/short-form-synthesis.md) has produced Russian speech without a new account or paid credentials. Treat it as a service-dependent fallback, not a permanent guarantee. Do not send private text to a new provider or incur new charges without appropriate authorization; do not install dependencies into the agent's production environment for a one-off clip.
5. **Verify the generated artifact and distinguish delivery quality.** For a requested delivery style such as warmth, playfulness or sensuality, inspect whether the selected provider actually forwards usable prosody/style controls before promising that effect; punctuation and a slower rate are not proof of the requested intonation. Keep tone experiments as previews when approval was requested. Check the response is audio, the file is nonempty, and ffprobe can parse a positive duration. When a native voice note is requested, convert to Ogg/Opus if needed. A parseable file proves audio was generated, not that every word was audited by listening; do not claim an auditory review that did not occur. Do not run speech recognition merely to manufacture a redundant check of a tiny synthesis request.
6. **Separate a preview from delivery to another person.** A request for a variant or draft addressed to someone is a preview in the current chat; an explicit send instruction authorizes delivery of that exact approved artifact, not another synthesis. If Luke rejects the intonation or says not to send/forget that version, withdraw that artifact from delivery and stop iterating unless he asks again; cancellation does not authorize deleting unrelated settings or pretending the conversation was erased. When asked to send a voice note to a named authorized contact, synthesize it once and use `hermes send --to telegram:<exact_chat_id> --json` with the message body `[[audio_as_voice]]\nMEDIA:/absolute/audio.ogg`. Do not return that MEDIA tag in the current chat instead of sending to the requested person. A successful CLI result gives the recipient/message_id; do not resend on an uncertain verification outcome. Native media-only outbound mirrors store `[Sent voice message]`, not the audio path or directive: filter only this sent receipt when verifying, rather than reading the recipient's private conversation. Preserve each person's established form of address.
7. **Deliver the requested number of native voice notes.** For Telegram, use an audio_as_voice marker and absolute MEDIA path for each separate audio file, in requested order. For a simple one-off recording request, the voice notes themselves are normally the complete response; omit process narration and captions unless needed to explain a real limitation. Under Le's standing private-chat preference, include the written answer as well as the voice attachment for ordinary replies, but keep reports text-only. Distinguish a generated local file from a delivered attachment.

## Acceptance

Confirm the text source and language, exact logical message count/order, nonempty decodable audio for each message, and native voice delivery formatting. If synthesis remains blocked, name the narrow failure rather than fabricating an audio attachment or claiming the text was recorded.
