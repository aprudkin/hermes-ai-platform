# Backup and migration design

Use this as a planning and verification checklist, not as evidence that any particular backup script or restore has already run successfully.

## Choose the smallest sufficient recovery set

| Need | Preserve | Independently verify |
|---|---|---|
| Keep current identity through deployments | Approved persona and its ownership policy; relevant deployment source | Live file versus mounted host file; repository diff; repeat-deployment behavior |
| Preserve accumulated personal state | Profile config, persona, memory, histories, custom skills/plugins/scripts, application state and job decisions | Consistent database capture; archive contents; exact profile scope; no accidental credential publication |
| Recover without the original service host | Personal state plus compatible runtime version/image, volume layout and a short boot procedure | A separate target can read and run the restored state; no dependence on paths or secrets found only on the lost host |
| Move a functioning installation | Recovery set plus an explicit cutover and rollback plan | Only one active poller/action owner; target services work; old instance retained until acceptance |

## Different runtime, bridge or partial state transfer

1. Classify the intended change before designing it: relocating the existing installation, delegating between two agents, using one as a client/controller of the other, or moving only selected instructions, memory and skills. A feasibility question is not permission to provision paid infrastructure, install extensions or switch the live bot.
2. When only personal continuity is requested, inventory the editable persona, memory stores, reusable skills and essential tools. Do not expand the scope to port every integration or database. Preserve the full source archive even when only selected state is loaded into the target.
3. Define learning operationally: retrieving previous experience, recording corrections and updating procedural skills are distinct from model-weight training. File copies alone do not provide discovery, injection, search or writeback; identify how the target will actually use and update each store.
4. Search current primary documentation and existing extensions before proposing custom glue. Treat CLI extensions and runtime libraries as different surfaces: an extension for Pi coding agent is not automatically compatible with Pi Durable, and connecting Hermes through a bridge does not give Hermes checkpoint recovery.
5. Evaluate candidate bridges by their actual direction and transport. Documented examples include Pi invoking Hermes CLI through the community Permes extension, a Pi controller driving remote Hermes over SSH/tmux, and pi-hermes-memory porting memory/search/procedural-skill mechanisms into Pi. These are source-documented examples, not locally verified installations or automatic imports of an existing profile. Recheck compatibility and source safety before recommending a concrete installation.
6. For a custom client, inspect the official Hermes programmatic-integration documentation before inventing flags or protocols: ACP, TUI gateway JSON-RPC and the HTTP API server expose different contracts. Choose the least complex interface that carries the required session state and tool results.
7. Test provider authentication, target prompt assembly, memory retrieval/writeback and a selected skill before claiming a migration works. A preserved model identifier or copied OAuth file does not establish target access. Test restart behavior separately from external-effect deduplication: persisted checkpoints do not imply exactly-once messaging or accounting.
8. Treat a later cancellation as closing the migration workstream; do not provision a standby target or keep pursuing integration alternatives without a renewed request.

## Review a target-server preparation plan

1. Establish the requested scope before connecting: document review, read-only host audit, or authorized implementation. Treat unchecked tasks and historical hardware/configuration descriptions as intentions or prior observations, not live evidence. Report document analysis separately from server inspection.
2. Identify which application each requirement belongs to. Separate host SSH/firewall/updates from application paths, database engines, entrypoints, build steps and resource limits. Do not transplant another bot's migration commands or memory limit into the agent runtime. Clarify shared-host versus dedicated-host placement when it changes resource and restart boundaries.
3. Compare proposed runtime options with both backup admission checks and restore serialization. Inspect rejection lists and the fields emitted into recovered Compose, particularly network mode, capabilities, security options, read-only root, tmpfs, namespaces and mounts. A restrictive option may stop future captures or disappear on recovery. Extend round-trip tests and support before changing production; do not weaken hardening merely to satisfy an old backup contract. Keep these findings revision-specific rather than recording a permanent limitation of the product.
4. Trace the actual network mode before selecting firewall acceptance tests. For host networking, absence of published ports is not isolation: inspect bind addresses and host INPUT. For bridge networking, check forwarding/NAT, Docker backend and user rules; one base chain's accept cannot override another chain's drop. Test build-network egress separately when a build is required. Recheck installed-version documentation instead of making experimental backend status a permanent rule.
5. Separate supported host OS from proven recovery compatibility. Official Docker support for a distribution does not establish that the existing recovery procedure has been tested there. Check image architecture, image-store identity semantics, numeric ownership and ACL/xattr handling before recommending an OS reinstall or claiming portability. Read the restore helper's destination admission logic: an empty existing directory can still be rejected.
6. Reconcile least-privilege administration with the actual automation caller. Inspect whether backup scripts invoke sudo, require noninteractive elevation, or run as a host service. A successful human sudo session does not establish unattended access. Choose a scoped execution route rather than granting unrestricted passwordless administration to make a test pass.
7. Present confirmed incompatibilities first, with exact code/config locations and the failure mechanism. Separate safe host preparation, isolated restored-runtime acceptance, and production cutover. Preserve the saved image/configuration for initial recovery; make network redesign, hardening changes and application upgrades separately testable rather than bundling them into an unproven move.

## Storage and custody

- Select an off-host destination under the owner's control; another directory, bind mount or container on the same machine is not a separate failure domain.
- Encrypt backups that contain history, tokens or private keys. Keep the decryption/recovery route available to the owner without depending on the agent being online.
- Keep executable recovery instructions and nonsecret deployment source in Git when helpful. Do not substitute a Git repository for backups of live databases and private state.
- Separate runtime-bundle contents from host reconstruction. An app/data/image bundle does not restore host SSH accounts or authorized_keys, firewall/provider policy, Docker installation, or a host backup package/configs/receipts/systemd timer outside those trees. Keep cloud decryption material independently accessible; never reconstruct deletion authority from a cloud listing. Verify new-host keys through a trusted route and deliberately update restored aliases that still point at the old server.
- When recovery guides are embedded into generated capture programs at installation time, distinguish updating Git documentation from updating the installed embedded guide. New controller-generated archives use the current checkout; an existing host capture program retains its earlier guide until deliberately regenerated. Never claim every future archive contains a newly edited guide merely because the PR merged.
- Retain more than a single overwritten snapshot so a bad state change is not immediately copied over the only recovery point. Choose retention with the owner instead of inventing a large storage policy.

## Change cloud layout, retention and verification scope

1. Reconcile the latest explicit instructions before changing the installed helper. Track destination, date naming, retention, verification and notifications as separate choices: a retention request alone does not disable verification, while an explicit request to remove reverse downloads supersedes a legacy round-trip requirement. On a partial resumption such as “everything except notifications,” pass the retained scope and exclusion to the worker explicitly; do not revive the excluded feature from an earlier request. When asked who requested a feature, retrieve the originating instruction or supplied installation report; distinguish inherited behavior from a feature added by this assistant and a direct feature request from a pasted description.
2. Explain opaque cloud names only after mapping them through the existing crypt configuration. Compare read-only logical listings with provider-visible paths and durable receipts; random names or large sizes alone do not prove that a folder is disposable, corrupt or even part of this workflow. Never print encryption secrets.
3. Implement owner-visible date directories at the correct layer of the destination. Preserve case, nesting and the requested date format, not merely a logical date hidden by directory-name encryption. Keep archive content encrypted and retain the old keys/configuration needed to read legacy copies. Verify the actual provider-visible result separately from a decrypted crypt listing.
4. If the owner is deleting backups manually, resolve whether they mean local host archives or cloud objects before allowing overlapping writes or removals. After they confirm deletion, refresh the exact affected destination metadata and re-plan from the observed state: old successful receipts establish historical uploads, not current remote existence. Preserve that history and record externally removed objects separately from deletions performed by this workflow. Do not recreate a retired namespace or keep attempting a relocation whose sources are gone. Check any retained local archive against its receipt before selecting it for an authorized new-layout upload; report that upload as a new operation, not a fresh capture or a verified cloud restoration. Before moving retained archives or expiring old ones, build an exact source-to-destination map from attributable manifests/receipts. Check whether the provider supports server-side encrypted-object copy or move before selecting it; do not claim that route works until exercised. When reverse downloads are excluded, use only authorized metadata checks for relocation and disclose their limits. Confirm the retained target exists before deleting its old source; ambiguous outcomes require reconciliation, not a repeated destructive command. Leave unrelated or unowned objects untouched and name unresolved legacy remnants precisely.
5. Reconcile owner-deleted cloud backups before retention or layout changes: preserve historical receipts, explicitly distinguish external removal from workflow deletion, and never let stale receipts authorize deletion in a new namespace. After expiring attributable dated objects, remove their exact date directory only through an empty metadata listing and nonrecursive `rmdir`; leave unknown contents untouched. Apply retention to the Moscow calendar date of stored capture timestamps, not encrypted names, lexicographic order of unpadded dates, or a newly copied object's modification time. Keep every copy from the current run's Moscow date and the two previous dates; expire only dates earlier than current-date minus two days. This is neither rolling 72 hours nor a fixed snapshot count. Test Moscow midnight, UTC midnight, month/year boundaries and repeated same-day copies. Allocate a fresh `YY-M-D`, `YY-M-D-2`, `-3`, etc. by exact directory stat under the stable workflow flock; empty, unknown and failed-upload folders are occupied. Pinned rclone crypt `lsjson --stat` reports an existing directory root with empty `Name` and `Path` and `IsDir=true`: represent that actual shape in fixtures and verify with read-only installed metadata. New receipts must bind and validate the actual canonical base or base-N (integer N>=2) directory against the capture date; retain compatibility with unsuffixed dated-v1 receipts. Exact archive deletion and nonrecursive empty-folder cleanup must both use the stored suffix, never recompute the unsuffixed base. Change the scheduled policy and clean up currently expired attributable copies as separate verified outcomes. Keep receipt/audit metadata when archive payloads expire.
6. Exercise the narrow changed path before atomic installation under the existing workflow lock. Test dated destination mapping, expiration boundaries, upload failure before deletion and absence of forbidden download/verifier calls. Update success-event and receipt semantics so local integrity, remote metadata, full downloaded verification and restored-runtime acceptance cannot be confused. Do not run a new multi-gigabyte capture or reverse download merely to test a layout change when fixtures and targeted metadata readback suffice.
7. Report the installed policy, actual remaining dated copies and any legacy exceptions. A prepared patch is not deployment, a metadata listing is not a checksum comparison, and an upload is not a restored application.

## Content-free task and snapshot notifications

- Treat newly authorized group-only task statuses separately from cancelled private backup-completion notices; preserve the cancellation and normal report destinations. Use a fixed verified bot/chat, silent static status templates and locally reviewed human-readable task-purpose aliases. Do not expose raw job IDs as the only description, private prompts, health details, financial records or task results.
- Resolve every active scheduled job from its actual definition/script and reconcile the collected count programmatically. Keep cancelled jobs disabled. A frequent reminder checker is not the notifier itself merely because it produces many status messages; trace its actual script before diagnosing a notification loop.
- If the installed plugin catalog lacks true cron lifecycle hooks, do not pretend session/tool hooks cover no-agent jobs. A narrowly scoped independent host observer may project the real profile-local execution ledger without running jobs or rerouting outputs. Persist a no-history activation cutoff and per-execution start/terminal receipts, distinguish actual started/failed/unknown states, and disclose that short jobs' observed-start notices may arrive after completion.
- For host backup task status, use systemd invocation IDs and actual terminal service results. Place planned-pause notices synchronously before Docker pause and resumed notices only after the same original container is inspected running/unpaused, including successful exception cleanup. A host sender must survive container freeze. Exercise ordering and negative cases with disposable fixtures instead of pausing production solely for notification tests.
- Open cron execution SQLite sources using `mode=ro` and `query_only`; a WAL reader can still require writable SHM/WAL sidecars. Reproduce this under the actual systemd mount namespace before claiming a read-only sandbox is compatible. Permit only the needed profile-local sidecar directory, never use `immutable=1` to ignore live WAL. Explicitly close SQLite connections; their context manager commits/rolls back but does not close them.
- Persist send intent before network effects, verify exact response identity/text and independently verify the exact sent message (Telegram identical edit/not-modified is useful when direct message GET is unavailable). Never blindly retry uncertain sends. Avoid replaying an already reported manual backup when enabling future automation.
- Keep reviewed label data dynamically readable where practical, so later naming corrections need no daemon restart. A changed on-disk Python module does not update a running cached interpreter. Honor pending tool approvals; report installed files and live adoption separately rather than bypassing a blocked reload or claiming the running formatter changed.

## Inspect local snapshot retention

1. Read the installed workflow's capture, receipt-write and cleanup order before answering how long host snapshots survive. Identify the actual state root from the helper/service rather than assuming the cloud path is a local directory.
2. Inventory only ready archive payloads, for example `Path(state_root).glob('runs/*/upload/*.tar.gz')`, and match their run identifiers and sizes to committed success receipts. List partial captures separately; do not include scratch files, receipt JSON or journals in the ready-backup count. Use selected metadata instead of dumping private archive contents.
3. Describe this user's local policy as replacement-based: keep the latest successfully uploaded local archive until the next archive passes the authorized upload/metadata checks; only then remove older attributable local payloads. A failed next upload leaves the previous copy available. This is usually about one daily interval, not a guaranteed time-to-live, and is separate from cloud calendar-day retention.
4. Check integrity/identity before deleting an older original, preserve the current run, and retain receipt/audit metadata after payload removal. Never infer deletion authority from a filename or cloud listing alone. On a cloud upload followed by failed housekeeping, distinguish an existing recovery copy from a fully successful workflow; reconcile the exact failed stage rather than repeating capture or upload blindly.
5. Report the observed ready-archive count and capture dates, the cleanup trigger and failure behavior. State whether interrupted leftovers were inspected or remain unknown; do not promise that the host contains exactly one archive during an in-progress or failed run.

## Maintain an installed host-side backup helper

Use this for a small reviewed code correction, not a full deployment or a live backup rehearsal.

1. Identify the installed helper, its private package directory, the workflow lock and the service/timer. Compare installed bytes with both the reviewed old revision and the intended replacement; refuse unrelated host changes rather than overwriting them.
2. Compile the replacement before changing the target. Acquire the existing workflow lock with nonblocking `flock` without unlinking or replacing its inode, then confirm the backup service is inactive and Hermes is running/unpaused. Leave an active backup alone rather than interrupting it to deploy a helper.
3. Keep a private byte-exact rollback copy outside the runtime's personal-state tree. Stage the new file on the destination filesystem, preserve ownership/mode, flush it, atomically replace the target and sync the directory. An initial installer that refuses existing paths is not an upgrade mechanism.
4. Exercise the installed functions in a new private temporary fixture directory. For a receipt-write repair, create an interrupted staging file, perform a real atomic write, load only committed receipts and check that pending-only data cannot authorize retention. Do not point fixtures at the production receipt ledger, invoke cloud deletion, pause Hermes or start a full capture just to test the patch.
5. Restore the saved bytes if the narrow self-test fails. After a successful update, read back the exact installed target through a fresh connection and confirm its content, permissions, source state and unchanged timer. Report helper installation separately from the next complete backup run and from restore verification.

## Run an explicitly requested full backup

1. Inspect the installed service and entry point, service state, available space and current source state. For the existing systemd installation, use `systemctl show hermes-backup.service -p ActiveState -p SubState -p Result -p ExecMainStatus`, `systemctl cat hermes-backup.service`, selected `docker inspect` fields for `hermes`, and disk space on the actual state filesystem. If a backup is already active, follow that run rather than starting a duplicate or interrupting it. A fresh-capture request is not satisfied by re-uploading a retained archive.
2. Compute the destination date using the capture timestamp in Europe/Moscow, not the conversation's UTC date. Explain the brief snapshot pause before starting; identify compression and upload as later, available stages. Use observed timings for a rough estimate and do not promise a fixed pause or transfer speed.
3. Record a host-side start boundary and initiate the installed service outside the source container with `sudo -n systemctl start --no-block hermes-backup.service`. Read back its active state and execution identity. Leave the daily timer unchanged: a requested extra backup does not cancel or reschedule the next daily run. Never execute the pausing capture inside the container it freezes, because that can freeze its own controller.
4. Launch a bounded monitor with a real process handle before ending the turn. Correlate a newly created safe journal and receipt with the recorded start boundary; reject old success evidence. Match the service invocation or journal run throughout polling so a later timer run cannot silently replace the observed operation. Inspect service failure even if no journal or receipt was created, because admission checks can fail before journal initialization. Bound polling and connection failures; an unknown outcome calls for readback, not a blind second start. A monitor inside the source container pauses with it and is not an independent outage notifier; the host service itself continues outside that container.
5. Require terminal service success, the matching journal's terminal `success`, the new committed receipt, running/unpaused Hermes and the exact receipt-bound cloud object with the expected size. Check only currently authorized metadata when reverse downloads are disabled. A successful launch, a progress heartbeat or an existing archive is not completion. Keep local archive integrity, upload metadata and restored-runtime verification distinct.
6. Answer availability questions with selected stage events only: pause intent/confirmation, unpause confirmation and current Docker state. Calculate elapsed pause with a tool. Avoid printing entire generated capture source, because embedded guide and helper strings can expand a few source matches into huge irrelevant output. Do not infer lossless inbound message handling from successful unpause.
7. Report the actual cloud directory, new capture identity/date, size and remaining uncertainty briefly. A one-time result for this explicitly requested operation is not permission to add recurring completion messages. Preserve partial files and stage evidence after failure until the exact interrupted effect is reconciled.

## Verify the first scheduled backup

1. Read the timer's actual timezone, next trigger and enabled/active state; compute the check time with a timezone-aware tool rather than mental offsets. A successful manual service start does not establish timer execution.
2. For a scheduled follow-up, use an explicitly one-shot check when verifying only the first run, retain the correct delivery chat, and read back the saved job. Do not silently turn it into a recurring digest.
3. Require a trigger and run newer than the expected schedule window, a matching durable receipt for the currently authorized verification level, terminal `success` in that run's safe journal, a successful terminal service result and running/unpaused Hermes. When full readback is enabled, require its matching round-trip evidence; when the owner has disabled it, verify upload completion and the permitted remote metadata without secretly downloading the archive or implying equivalent cryptographic verification. An old receipt or a receipt written before failed housekeeping is not full workflow success. Report an ongoing run as ongoing, not as success or definitive failure.
4. Read only allowlisted metadata; never dump cloud configurations, environment variables, private keys or archive contents into a monitoring report. Distinguish this observation from archive restoration.
5. State the failure-domain boundary: a check running inside Hermes cannot independently notify while that same host/container is down or paused. Use an independent runner for that guarantee; do not present an agent-local one-shot check as an external watchdog.

## Prepare a shared-host restore rehearsal

Use this procedure to design and review a rehearsal; it does not establish that any runtime-specific startup command has been exercised.

1. Separate host preparation, secret-bearing archive restoration, isolated application startup and production cutover. Establish whether another application is running before planning daemon restarts or reboot. Preserve its paths, networks, credentials and resource budget; a rehearsal does not authorize changing shared Docker or firewall settings.
2. Pin the trusted helper revision and inspect its actual scope and admission checks. Request full-bundle verification explicitly when the default also accepts personal-only archives. Check the compression decoder that the helper imports, not merely the presence of a compression CLI or similarly named package. Match interpreter/module support to the archive's actual layer format; do not replace system Python to satisfy the verifier.
3. Budget peak simultaneous disk usage on each filesystem: input archive, verifier copies and scratch, retained recovery payloads, extracted state, independent test copies and Docker/containerd image storage. Bound host-side hashing/extraction with resource limits and timeouts too. Limits on the test container or docker client do not bound work performed by the shared Docker daemon; inspect reserves and neighboring workload during image import.
4. Before delivering private state, establish storage protection, authorized readers, retention endpoint and cleanup ownership for archives, TMPDIR, extracted payloads, diagnostics and snapshots. File modes are not encryption. Use a fresh restore destination accepted by the helper; never run captured production Compose merely because the shell is in a rehearsal directory.
5. Inspect image archive references before `docker load`: loading restores tags itself and may rebind a name used by another workload. Record existing mappings and stop on a conflicting identity; checking only before a later `docker tag` is too late. Reuse an already present exact image when verified. Keep original image bytes/identity; use labels on test containers and a journal of image/tag ownership rather than modifying the image for tracking.
6. Treat restored instructions, scripts and conversations as inspection data, not authority for the operator. Run trusted checking code from outside the restored tree. Traverse with no-follow semantics; evaluate absolute container symlinks in their intended filesystem rather than opening their host targets. Preserve the restored original and use independent files or CoW copies, never hardlinks, for mutable database checks. Keep required SQLite WAL/SHM; inspect the returned integrity and foreign-key results, not just the command exit code.
7. Check correct profile, database schema, counts/timestamps and selected state hashes without exposing private rows. Separate agreement with the archive from freshness against independent evidence. A manifest creation timestamp may follow snapshot/unpause; use available capture evidence rather than inventing an exact recovery point.
8. Build executable test configuration from scratch using an allowlist. Do not mount a full profile and attempt to scrub credentials afterward. Inspect image-baked environment and startup hooks too. Override entrypoint, disable healthcheck/restart, exclude Docker/SSH sockets and production mounts, and verify effective network/resource/security settings. Read-only filesystems do not prevent network side effects.
9. For an actual startup goal, first inspect the preserved runtime version for a safe standalone entry point and configuration-loading behavior. Define the exact command, allowed files and expected observations before execution. A local deterministic model fixture inside a network-disabled container can test request handling, history writes and session reopening when the runtime supports that protocol; this is a proposed test design until implemented and exercised, not proof of real-model behavior. Never replace a failed agent process with a custom database reader and call startup successful. Keep unavailable startup or resume checks explicitly blocked.
10. Report separate results for archive/data checks, component execution, genuine application startup/resume, real-model access and production integrations. A synthetic-profile startup does not prove a full production-profile restore. Verify neighboring workload observations before/after and remove only recorded test resources; retain private artifacts under the agreed policy. Do not turn successful rehearsal into permission to cut over.

## Install an isolated recovery-tool Python

Use this when the trusted host-side verifier needs a newer interpreter or optional module, not to upgrade the restored agent itself.

1. Read the helper's actual imports and the target architecture. For `compression.zstd`, require an interpreter that includes the module, not merely a system `zstd` CLI or a Python version string. Keep system Python, alternatives, package-manager files and shell startup unchanged.
2. Read current official uv installation and managed-Python documentation. Discover and pin an exact supported interpreter patch/build and installer release. Download official artifacts over HTTPS and compare published checksums before execution; upstream checksums are not independent signature verification. Do not turn historical version pins into defaults for future runs.
3. Use a fresh task-owned 0700 tooling root, separate from other administrators' directories. Put installer, interpreter, downloads, caches, temporary files and evidence under it. With uv, use `uv --no-config python install --no-bin <exact-key>` and explicit `UV_PYTHON_INSTALL_DIR`, `UV_PYTHON_BIN_DIR`, `UV_CACHE_DIR`, `UV_PYTHON_CACHE_DIR` and `TMPDIR`; use the documented build selector when pinning a standalone build. Verify any local mirror configuration against current docs. Do not modify global PATH or use global pip as a workaround.
4. Execute the installed interpreter in isolated mode. Test compression/decompression and streaming roundtrips, interoperability with the system zstd CLI, tarfile gzip/zstd roundtrips, and rejection of truncated data. Run the trusted helper's relevant function on synthetic raw/compressed fixtures. Check SQLite integrity/required extensions, a disposable venv and certificate-validating TLS where the workflow needs them. Label scratch writes and public TLS probes accurately rather than calling the entire test read-only.
5. Compare protected paths and interpreter links against the prechange baseline. Save exact executable/version, checksum evidence, stdout/stderr and remote exit code; propagate failure through the controller instead of allowing a successful wrapper to hide it. Independently repeat a narrow remote probe after a worker reports success.
6. Record this as recovery-tool readiness only: neither restored application compatibility nor a successful archive restoration follows from it. Verify with a separate probe, not by rerunning one-shot bootstrap scripts over an existing installation. Rollback first checks consumers, preserves evidence, and disables/removes only the new owned tooling root; a system Python that was not changed needs no repair.

## Two-phase freeze, readiness and owner approval

### Establish an executable path before estimating readiness

1. Start with the execution dependency, not a test harness: identify the host-side process or human operator that remains available after source shutdown, its source/target access, owner control route and recovery command. Verify this outside the source container before promising unattended completion or a downtime window. If it is missing, implement the smallest authorized external path or report that exact gap immediately; more fixture tests cannot supply it. Inspect existing capture/restore helpers and map quiescence, single-owner fencing, consistent transfer, verification, notification, approval and recovery to concrete commands. Preserve the user's agreed requirements, but do not impose an unrequested universal controller or disposable VM on a one-container move.
2. Check the actual source's runtime and writable-layer admission read-only before fixing a rehearsal-only compatibility difference; preserve allowlisted observations and code hashes without exporting credentials. Implement the smallest reversible path using the agreed transfer representation: fence a disposable source, produce and verify a real recovery payload, transfer it when transport is in scope, exercise the notice through a local HTTP fixture, and recover that source after missing approval or an injected failure. A metadata-preserving staging archive transported by scp can be the single migration copy, not an additional mandatory backup. Use generated state and fake external services where necessary, but execute the production adapter code rather than testing only the controller interface. This is integration evidence, not live-host acceptance.
3. Add target restore/start and dialogue acceptance only after that path works. Inject interruption before and after each consequential effect; test persisted intent, receipt reconciliation and repeat invocation. Keep target-unreachable and unsuccessful-fence cases blocked rather than counting a watchdog timeout as proof of shutdown.
4. Report controller tests, adapter integration, host installation and live acceptance separately. Before estimating a scheduled deadline, account for unresolved owner-access decisions, unimplemented operations, review time and measured capture/transfer duration. An active worker and a generous time window do not establish that the critical path is feasible.
5. For reversible source recovery, bind the controller's saved-settings digest to the host original, persist local revocation and start intent under the stable source/backup locks, and hold the site-wide target-fence/revocation authority throughout recovery. Recheck current cancellation/effect reconciliation before every enabling effect and after readback. A start-intent crash followed by a stopped source is uncertain even if the test killed before dispatch; refuse automatic replay, while an observed running original can reconcile without another start.
6. Keep non-starting custody receipts false for readiness and independent-host protection when composing the controller path. Use a separate custody authority for real failure-domain proof; label a second-directory fixture as a modeled premise. An absent production authority must fail admission, and a pre-cutover-only adapter must refuse target-activity recovery rather than discard delta or route it to the no-activity shortcut. Carry the remaining production port and concrete read-only admission inventory into the handoff instead of accumulating unrelated libraries.

7. Where an existing controller is used, connect read-only admission diagnostics to its preflight and verify that incomplete evidence cannot initiate freeze. Treat a JSON inventory as observations, not readiness or remote revocation. Distinguish unknown pending work from positively observed pending work; keep private values out of public diagnostics. After fixture integration, advance to the actual application and external execution path. Add fence/reboot/remote-operation rehearsals only for a specific unresolved risk in the intended deployment, not as an automatic chain of new prerequisites. Compare a failing fixture's configuration with the real source before widening a validator or delaying the move.

### Admission and continuity requirements

- Separate a dated freeze/backup trigger from cutover approval. Resolve both absolute date and timezone when a conversation crosses local midnight; prepare but do not activate a timer before independent review. A missed or unproven admission window must fail closed before freeze, not retry later until it happens to succeed.
- When all ordinary inputs are stopped, provide an independently authenticated owner action route and external readiness sender. A stopped gateway cannot also receive its own Telegram approval. Do not add a competing getUpdates consumer or advance offsets past unrelated buffered updates; an SSH owner-key route requires explicit enrollment and agreement to that different channel.
- Bind approval to the enrolled owner/original chat, current run nonce, exact verified archive digest, notice ID and expiry. Bound preparation/await-confirm separately from post-start dialogue acceptance, persist target-start intent before the effect, and route uncertain start through fencing/delta-preservation recovery. Terminal abort/acceptance must suppress late actions. Boot recovery may resume an admitted run but must not initiate a PREPARED freeze.
- Preserve the installed capture's admission and cleanup behavior. A helper that requires a running/unpaused container and auto-unpauses before packaging is not a cold final snapshot; do not fake runtime metadata or bypass safety checks to use it after a full fence. A tested controller kernel without a real reviewed site adapter remains activation-blocked.
- Check the installed Telegram adapter and PTB shutdown code against the latest documentation before promising backlog preservation. A documented cold-boot option may not exist in that revision; PTB can acknowledge updates placed in an in-memory queue before application processing, including during shutdown cleanup. Treat live offset/inflight counts as unknown unless actually exported; a session DB high-water mark or stopped container is not a durable inbox/drain receipt. Exercise exact installed method bodies offline with fake transport when safe, and preserve source hashes separately from production acceptance.
- For a stopped-gateway Telegram approval design, prefer one external durable ingress owner with a deterministic owner/original-DM control handler, never a second competing poller. Persist update payloads before the PTB queue-put boundary allows an offset advance; retain unknown fields and arrival order, distinguish queue task_done from business completion, and quarantine uncertain effect dispatch rather than replaying it blindly. Exercise installed polling/cleanup method bodies with fake transport, process-death SQLite recovery and forged/stale/forwarded approval negatives. Treat this as kernel evidence until authenticated transport, full gateway replay and cross-host fencing are implemented. Test restart replay from the persisted pending rows, not only duplicate receive: deduplication can correctly suppress re-enqueue while the previous in-memory queue has vanished. ## Restore and cutover gates

1. Verify archive integrity and inspect its manifest before extraction; check scope, paths and required runtime version.
2. Restore into an isolated environment with outbound actions, bot polling and scheduled writes disabled initially.
3. Apply the current cancellation and access-withdrawal decisions before enabling integrations. Do not resurrect removed mail access or cancelled notifications from an older backup.
4. Check that the intended profile, identity, application data and databases load. Revalidate external authentication only where access is still authorized.
